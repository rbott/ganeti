# wconfd-bench

Standalone dev tooling to measure how wconfd RPC latency scales with
`config.data` size, in the context of PR #1972 (wconfd config-lock timeouts
on large clusters). Not part of the regular build or test suite.

## What it does

Spins up a 1-node vcluster inside the CI container (`ganeti/ci:trixie-py3`),
grows `config.data` in tiers, and at each tier measures per-RPC latency
directly at the wconfd unix socket:

- `Echo` — trivial round-trip baseline
- `ReadConfig` — full config read out of wconfd (scales superlinearly)
- `TryUpdateLocks` — shared lock request + release round-trip

Output is a CSV (p50/p95/min/max per method per tier).

## Usage

Run all commands **from the repository root** (the `docker build` context `.`
must be the repo root, or you get `lstat tools: no such file or directory`).
Build Ganeti in the image first (one time; the build is cached in the image).
Then run the sweep — it's a single command:

    docker build -f tools/wconfd-bench/Dockerfile -t wconfd-bench .

    # Do NOT mount /src here: the image already contains the built tree at
    # /src (doc/examples/ganeti.initd, dist/build/*, tools/vcluster-setup are
    # generated by the in-image `make`). Mounting your host repo over /src
    # shadows that build with an un-built tree and stage.sh fails. Only /out
    # (results) is mounted.
    docker run --rm --ulimit nofile=1024:4096 --privileged \
      -v "$PWD/results:/out" wconfd-bench smoke   # ~100KB
    ... all          # baseline + 100KB then 500KB steps to 5MB
    ... 500kb 1mb    # explicit tiers

For iterative work, use the plain CI image (not wconfd-bench), mount the
source at /src, build in place, and drive bench.sh directly:

    docker run -d --name wconfd-bench --ulimit nofile=1024:4096 --privileged \
      -v "$PWD:/src" -w /src ganeti/ci:trixie-py3 sleep infinity
    docker exec wconfd-bench bash -lc './autogen.sh && ./configure && make -j$(nproc)'
    docker exec wconfd-bench bash /src/tools/wconfd-bench/bench.sh smoke

`--privileged` is required: `vcluster-setup` assigns the node an IP via
`ip addr add`. The nofile ulimit matches the devcontainer config.

## Files

| File | Role |
|---|---|
| `Dockerfile` | image: CI base + `autogen/configure/make` + vcluster-setup on PATH |
| `bench.sh` | single-node orchestrator: stage → vcluster → init → sweep → CSV |
| `bench-multinode.sh` | multi-node variant: 8-node vcluster + concurrent job-load phase |
| `stage.sh` | stages install tree under `/usr/local` from `/src` build (idempotent) |
| `bench_driver.py` | measures Echo / ReadConfig / TryUpdateLocks at the wconfd socket; also `wait` and `instances` (wconfd-direct listing) subcommands |
| `job_load.py` | submits N concurrent config-modify jobs, samples wconfd latency under load, counts >30s lock timeouts |
| `grow_offline.py` | clones a template instance into config.data offline (fast); distributes clones across node UUIDs |
| `grow_restart.sh` | offline grow + restart of wconfd/luxid only |
| `grow.sh` | grows config via real `gnt-instance add` (slow; `GROW_MODE=gnt`) |
| `format_results.py` | renders a results CSV as an ASCII table (`--load` for job-load CSVs) |

## Multi-node benchmark

`bench-multinode.sh` builds an 8-node vcluster (1 master + 7 nodes, 6 master
candidates), grows config.data offline, and at each tier measures wconfd
latency twice: idle, then while `JOB_BATCH` (default 8) concurrent
`gnt-instance modify -B memory=N` jobs run. The modify job takes the same
exclusive-config-lock + full-serialize path as `INSTANCE_MIGRATE` /
`INSTANCE_REPLACE_DISKS`, so it reproduces the PR #1972 contention without
needing running instances or a real hypervisor.

    docker run -d --name wconfd-mn --init --ulimit nofile=1024:4096 --privileged \
    docker exec wconfd-mn bash -lc './autogen.sh && ./configure && make -j$(nproc)'
    docker exec wconfd-mn bash /src/tools/wconfd-bench/bench-multinode.sh 1000 3000 5000

**Use `--init`** (tini) for the container. Without a reaping PID 1 the Ganeti
daemons turn into zombies under load and every subsequent wconfd/luxid call
hangs. This was the single biggest source of flaky runs.

The job-load phase needs SSH between nodes: the script installs
`openssh-server` in the container and starts `sshd` (all node IPs are
loopback). Output is two CSVs + two tables (idle and under-load).

## Config growth: offline vs. gnt

Default is **offline** growth (`GROW_MODE=offline`): wconfd is stopped, a
template instance is cloned into `config.data`, and wconfd/luxid are
restarted. This reaches 5MB in seconds. `GROW_MODE=gnt` uses real
`gnt-instance add` per tier — much slower, because each add exercises the
same O(config-size) serialize+flush path being measured (the growth rate
decelerates as the config grows; that deceleration is itself signal).

Offline-cloned instances are config-only. Fine for read/lock benchmarks; for
job-realism tests use `GROW_MODE=gnt` or a real+cloned mix.

## Notes

- Numbers are relative, not absolute: container CPU scheduling skews
  wall-clock latency. The signal is the scaling curve vs. config size.
- The container's PID 1 (`sleep infinity`) does not reap children, so zombie
  daemons accumulate across stop/start cycles. `grow_restart.sh` restarts
  only wconfd/luxid and never runs full `stop-all` (luxid blocks on wconfd
  during stop). If daemons get stuck, `docker restart <container>` clears
  zombies while preserving the vcluster and config.
- luxid spawns jobs as `<versionedsharedir>/ganeti/jqueue/exec.py`;
  `stage.sh` symlinks `/src/lib` there so job submission works from the
  source build.
